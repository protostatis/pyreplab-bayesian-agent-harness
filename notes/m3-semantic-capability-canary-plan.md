# M3 Semantic-Capability Canary Plan

Date: 2026-08-12

Status: small screen passed; larger replication completed with valid no-go

## Decision

Test whether two controller-owned, mechanically distinct specialists create
repeat-stable complementary task niches after repairing the shared browser
lifecycle. This is an excluded screening/futility canary. It cannot amend the
frozen M3 no-go, unlock Phase 2, establish a causal capability effect, or train
an allocator.

## Treatments

Both arms retain the same interactive Unbrowser substrate, prompt, resource
limits, and controller-owned public HTML fetch. They differ only in the added
specialist tool:

- table arm: deterministic filter, numeric sort, offset, limit, and projection
  over public HTML tables;
- form arm: deterministic public form description and same-origin GET form
  submission.

Neither specialist reads fixture templates, seeds, private oracles, task files,
cookies, or credentials. Every successful specialist operation returns a
payload-bound SHA-256 receipt. Model-input errors remain ordinary tool errors;
process, transport, fetch, and response-timeout failures carry a structured
infrastructure marker and invalidate the screen.

## Mechanics

Each mechanics version has two fresh tasks, two treatments, and one replica:
four attempts. The first task is table-oriented and the second is form-oriented.
A receipt is required only for the matching specialist-task pair; the other arm
must solve through the shared substrate without a successful wrong-specialist
receipt.

Mechanics v1 is preserved as a diagnostic run. Its first gate exposed that the
semantic gate counted Pi's thirteenth blocked `Operation aborted` event as an
admitted call, despite the shared budget extension enforcing the 12-call cap.
The gate now uses the same bounded fallback already used by the observation
adherence code. Fresh v2 coordinates are required before outcome execution.

## Outcome Lock

Only a passing v2 mechanics gate may unlock an eight-task, two-replica screen:
32 attempts. Every task-policy cell is run twice. All tasks and attempts remain
`T_canary` / `canary_excluded`.

The outcome gate requires:

1. At most two discordant policy-task cells across replicas.
2. At least one stable table-only task.
3. At least one stable form-only task.
4. Between two and fourteen successes per 16-attempt arm.
5. At most four successes difference between arms.

Passing qualifies only this capability family for a larger prospective panel.
Failure after valid mechanics is a futility no-go. Infrastructure, identity,
receipt, completeness, or accounting failure is invalid and has no outcome
interpretation.

## Result

Mechanics v2 passed, and the complete 32-attempt outcome screen subsequently
returned `screen_pass` after repairing deterministic gate accounting. The
result and its boundary are recorded in
[`m3-semantic-capability-canary-result.md`](m3-semantic-capability-canary-result.md).

A larger prospective replication then used 16 fresh tasks, three replicas, and
96 attempts. It returned a valid `replication_no_go`: the matching specialist
won on all 16 tasks, but the predeclared repeat-stability and strict table-only
criteria failed. See
[`m3-semantic-capability-replication-result.md`](m3-semantic-capability-replication-result.md).
